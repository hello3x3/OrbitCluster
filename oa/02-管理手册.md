# 02 管理手册（平台管理员日常运维）

> 页面入口：登录**默认管理员 root**（平台最高管理员；也可登录 root 授予的其它管理员账号）后顶部出现：
> 用户管理 / 代申请资源 / 我的资源 / 申请资源 / 集群状态 / 个人资料。
> **「资源套餐」只对 root 显示**：普通管理员看不到入口，直接访问 `/admin/plans` 也是 403。
> 仅 `root` 可授予/撤销管理员（见 §4）。
> 命令行操作均在 <ADMIN> 节点以 root 执行。

## 1. 用户管理

「用户管理」可对**普通用户**操作：开通、重置密码、停用/启用、删除。
**管理员账号无操作按钮**（相互不能重置/停用/删除，由 root 或 OS root 管理）。

| 操作 | 说明 |
|---|---|
| 开通用户 | 用户名=Linux 账号名（只能用**小写字母/数字/下划线**，且以小写字母或下划线开头，1-32 位；不接受大写与 `-`）。方式一「自动建号」：`<ADMIN>+<GPU01>/<GPU02>` 建号（UID 一致）、/share 配额、sacctmgr 关联；方式二「OS 账号已存在」：初始化家目录/.portal、**按表单所选额度设置 /share 配额**（会覆盖该账号原有配额；额度可选「不限」＝不限额）、补 sacctmgr 关联，并**自动导入其 authorized_keys 现有公钥**。注意：选「OS 账号已存在」时 OS 上必须真有同名账号，否则开通会被拒 |
| 初始密码 | 管理员填写或留空自动生成（仅显示一次）；同时写入明文密码文件 |
| 重置密码 | 只对普通用户：随机生成、仅显示一次（会回写密码文件） |
| 停用/启用 | 停用后无法登录；已运行作业不受影响 |
| 删除 | 对“自动建号”用户：先注销集群账号（终止全部作业，删除三节点账号+sacctmgr+/share 家目录）再删门户记录；对 existing/管理员：仅删门户记录，保留 OS 账号与数据 |
| **改配额** | 改该用户 **/share 磁盘配额**（软=硬、实际写 OS `setquota`，读回 `repquota` 确认）。普通用户行任何管理员可改；管理员行仅 root 或本人可改；系统保留账号（root/portal 等）不可改 |
| 列含义 | SSH密钥=登记公钥数（写入其 ~/.ssh/authorized_keys）；端口数=端口池登记数；活跃资源=排队/运行实例数；**配额（OS 实读）**=repquota 读出的「已用 / 硬上限」，DB 不存实际值、不以此为准 |

> 普通用户“申请/登记公钥”的前提是集群存在同名 OS 账号。默认管理员 root 因集群存在同名
> OS root，可像普通用户一样自助申请/登记公钥；无同名 OS 账号的“纯平台管理员”（如另建的
> `admin` 账号）则不能自助申请/登记公钥，只能走“代申请资源”。

## 1b. 配额 / 额度说明（磁盘 + Slurm）

- **磁盘配额**：`/share` 采用 **ext4 用户配额（软=硬）**，门户展示与修改都**直读/直写 OS**
  （`repquota` / `setquota`，经 `/opt/cluster-admin/set-quota.sh`），门户 DB 不保存实际配额值；
- 普通用户在「我的资源」页可见自己的：已用/硬上限（GiB）、Slurm 关联账号、QoS
  （含优先级）、关联优先级、总额度；数据分别来自 OS `repquota` 与 Slurm `sacctmgr`（非门户虚构）；
- 管理员在「用户管理」改配额后需等待数秒（setquota 即时生效），页面刷新即显示 OS 实读新值；
- “总额度”= Slurm QoS/关联上的资源限额（MaxTRES/GrpTRES/作业数/时长等），当前均未设置＝**不限**。

## 1c. 镜像体系（公共 / 个人）与保存

- **公共镜像**：`<IMAGES_MOUNT>/*.sqsh`（root 维护，755），所有人可选；
- **个人镜像**：`<IMAGES_MOUNT>/<用户名>/`（700，仅该用户与 OS root 可读），由用户自己
  「保存镜像」产生，也计入该用户的 /share 配额（文件属主为用户）——删除用户时该目录随账号一并清理；
- 申请页/代申请页镜像下拉分组展示；白名单按“公共 或 该用户个人”校验，用户看不到别人个人镜像；
- **保存镜像（运行中）**：`portal-ctl save-image <用户> <jobid> <名称> [force]` 把正在运行容器
  （提交作业带 `--container-name=portal --container-writable`，rootfs 落在计算节点
  `ENROOT_DATA_PATH` 的 `pyxis_<jobid>_portal`）以该用户身份 `enroot export` 成 .sqsh；
  作业结束（停机/到期）后 pyxis 自动清理该 rootfs；
- **到期自动保存**：门户后台每 ~25s 扫描，对「开始运行时刻 + 所选时长」已到且仍 RUNNING 的实例
  自动导出为 `auto_<任务名>_<时间戳>.sqsh` 后自动停机；导出的同时会给它写一条注释
  `系统 <时间> 到期自动保存；建议打包成正式镜像后清理`（`_auto_save_note()`，写在镜像的同名 .json 里，
  用户和管理员都能看到，方便清理腾配额）；因此提交给 Slurm 的时长 = 所选小时 + 15 分钟
  （`PORTAL_EXPIRE_BUFFER_MIN` 可调，保存需在停机前完成）；
- 镜像目录/文件由 OS root 在 <ADMIN> 上创建（`install -d -o <用户>`）；计算节点侧以用户身份写 NFS
  （root 用户 root 的保存走“节点本地导出→scp 回 <ADMIN>”，规避 root_squash）。
- **用户自助管理自己的镜像**：「我的镜像」页（`/images`）允许任何用户对自己的个人镜像
  **写注释**（`/images/<名>/comment`）、**改名**（`portal-ctl rename-image <用户> <旧名> <新名>`）与
  **删除**（`portal-ctl delete-image <用户> <名称>`）；两条命令只接受
  `<IMAGES_MOUNT>/<用户名>/<名称>.sqsh`（名称：英文/数字/点/横线/下划线/加号，≤32 位，不能以点/横线/加号开头），
  校验普通文件、非软链、属主是该用户
  —— 越界路径、别人的目录、软链一律拒绝。镜像被「排队中」的资源使用时禁止改名，被「排队/运行中」的
  资源占用时禁止删除；改名会同步更新实例记录里的镜像路径。
- **root 的全局视图**：`root` 打开同一页时列出**公共镜像 + 所有人的个人镜像**（多一列「归属」），
  并可对任意一个**改注释 / 改名 / 删除**（走 `/admin/images/<owner|public>/<名>/{comment,rename,delete}`，
  非 root 一律拒绝；助手侧命令是 `portal-ctl admin-image-rename|admin-image-delete <owner|public> …`）。
  **两边的字符集已统一**：英文/数字/点/横线/下划线/加号，不能以点/横线/加号开头，不含路径分隔符/空白
  （公共镜像如 `cuda12.8.0-devel-ubuntu24.04`）。差别只在长度：**新建的个人镜像名 ≤32 位**，
  公共镜像名 ≤128 位；**改动前保存的既有个人镜像名（可能超过 32 位）仍然可以改名/删除/写注释**，
  不会被新规则锁死。
  改公共镜像名会同步所有引用它的资源记录；删任何镜像前都会检查它是否正被「排队/运行中」的资源占用。
  清理某个账号的全部镜像仍走「用户管理 → 删除」（连带清目录）。
- **镜像的注释等元数据存在"镜像同目录的同名 JSON"里**：`<名称>.sqsh` ↔ `<名称>.json`
  （例：`/share/images/alice/torch_base.sqsh` + `/share/images/alice/torch_base.json`），
  内容形如 `{"name","note","user","job_id","node","size","created_at","updated_at"}`。
  写入走 `portal-ctl set-image-note <owner|public> <名称> <文本>`（**最多 64 个"看得见的字符"**：中文/表情/空格都行，一个表情算 1 个；超出直接拒绝）；`save-image` 成功时也会写一份
  （覆盖保存会**保留**原有注释）。**改名时 JSON 跟着改名、删除镜像时 JSON 一并删除**，
  所以镜像和它的注释永远在一起，跟着镜像目录一起搬迁/备份也不会脱节。
  **镜像打包是原子的**：`save-image` 先导出到 `<名称>.sqsh.part`，成功才 `os.replace` 成 `.sqsh`
  —— 所以「正在打包」的镜像不会出现在任何人（含 root）的列表里，中途失败也不留半成品；
  `.json` 里的 `note` 就是「我的镜像」页那一列。

## 2. 资源套餐（**仅 root 可访问/维护**，普通用户只选不可改）

字段：名称 / GPU（0 纯CPU 或 1 单卡）/ **GPU 型号**（下拉，选项自动来自集群 gres，
当前仅 RTX 3060）/ CPU 核数 / 内存 GB / **最长时长 maxtime_h** / 启用状态 / 说明。
- 普通用户申请时长 **≤ maxtime**；超长时提交按钮置灰并提示“找平台管理员代为申请”；
- **管理员「代申请资源」不受 maxtime 限制**（仍限 1–720h）；
- 停用/删除套餐不影响历史实例；有申请记录的套餐不能删除（可停用）。

## 3. 代申请资源

管理员帮“有集群 OS 账号的普通用户”提交：
选目标用户（列出其密钥/端口数）→ 选该用户**端口池中未被占用**的端口 → 镜像/套餐/任务名
(3-10字符)/时长/节点(默认自动)。
- 底层：OS root 经 portal-ctl 以 `runuser -u <用户>`（等价 `sudo -u`）提交，
  配额/计费归属被代用户，作业出现在该用户“我的资源”；
- 用途：普通用户要超过套餐 maxtime 的时长、或代为办复杂申请。
- **任务名唯一性**：同一用户下任务名不能重复（不区分大小写），用户自助申请与管理员代申请
  共用同一规则；停机/取消**不释放**名称，必须删除该条实例记录才能复用同名
  （DB 层有唯一索引 `ux_inst_user_task` 兜底，应用层在提交前先查重并给出友好提示）。
  老库若已存在重名，索引建不上，此时只降级为应用层查重，启动日志会打印警告。

## 4. 平台管理员权限（仅 root）

门户账号 **root**（最高管理员）在用户管理里可对其它账号：
- 「设为管理员」：授予平台管理员权限；
- 「取消管理员」：撤回到普通用户；
- root 不能修改自己的权限；其它管理员无法执行以上操作。
> 门户 root 拥有集群同名 OS root 账号，因此也能**像普通用户一样自助申请资源**
> （先在个人资料登记端口；其 /root/.ssh/authorized_keys 公钥在首次登记时自动并入，不会覆盖）。

## 5. 密码体系（重要）

- **唯一明文权威**：`/etc/cluster-portal/users.passwd`（`root:portal` 660，目录 770），
  每行 `用户名:密码`（非空、≤128 字符、不含冒号/首尾空格；# 注释）；
- **双向同步**：门户内建号/重置/用户自改密/删除 → 自动回写该文件；
  OS root 直接 `vi` 该文件 → 后台 watcher 约 20s 应用到门户账号；
- 立即生效（root）：
  ```bash
  cd /opt/cluster-portal && PORTAL_DATA=/var/lib/cluster-portal ./venv/bin/python -c \
   "import sys;sys.path.insert(0,'.');from portalapp.db import DB;from portalapp import pwfile;print(pwfile.sync_once(DB('/var/lib/cluster-portal/portal.db')))"
  ```
- 查看生效日志：`journalctl -u cluster-portal | grep 密码文件`；
- **管理员门户密码**不能由其它管理员重置，只能由 OS root 改本文件；
- 该文件只影响门户登录，与集群 OS 密码无关；OS 密码由集群 root 自行 `passwd` 管理。

## 6. 备份 / 恢复 / 迁移

备份（<ADMIN> root）：
```bash
bash oa/scripts/backup-portal.sh /var/backups/cluster-portal
# 产物 portal-<时间戳>.tgz：代码、portal.db、secret、users.passwd(明文!)、systemd、sudoers
```
恢复（新机或故障机）：
```bash
tar xzf portal-<时间戳>.tgz -C /tmp/restore
cp -a /tmp/restore/etc/cluster-portal /etc/        # 明文密码文件
install -d -o portal -g portal -m 750 /var/lib/cluster-portal
cp -a /tmp/restore/data/portal.db /var/lib/cluster-portal/
cp -a /tmp/restore/data/secret   /var/lib/cluster-portal/
chown -R portal:portal /var/lib/cluster-portal
rsync -a /tmp/restore/app/ /opt/cluster-portal/
install -m 755 /tmp/restore/portal-ctl /usr/local/sbin/portal-ctl
systemctl daemon-reload && systemctl restart cluster-portal
# （sudoers/unit 可先按 install.sh 重新生成，或复制 /tmp/restore/etc 对应文件后 daemon-reload）
```
升级/重装：重新 `bash /tmp/cluster-portal-src/deploy/install.sh <代码目录> 8000`（幂等，不覆盖 DB/密码）。

## 7. 服务与日志

```bash
systemctl status cluster-portal            # 状态
journalctl -u cluster-portal -n 100        # 服务日志（含密码文件同步、错误）
tail -f /share/home/<用户>/.portal/logs/<作业号>.out   # 作业原始日志（容器内 sshd 的输出）
# 门户侧操作日志（提交/停机/保存镜像/到期自动保存等）存在门户库 instance_events 表，
# 在页面「日志」弹窗里与容器日志一起展示（含保存耗时、失败原因、enroot 输出尾部）；
# 每实例保留最近 200 条，实例被删除时随记录级联清理；rm-log 删掉 .out 后事件仍在。
# 手工查询：sqlite3 不可用时用 venv python（见 03-使用手册「日志」一节）
squeue -o "%.8i %.10u %.12j %.3t %R %C"    # 队列
scancel <作业号>                            # 直接停（root 可）
scontrol update nodename=<GPU01> state=idle   # 拉回误标 DOWN 的节点
```

## 8. 常见排障

| 现象 | 处理 |
|---|---|
| 登录不上 | 确认该用户行密码文件正确；文件被改后等 20s 或手动 sync_once |
| 普通用户申请被拒“无同名 OS 账号” | 该门户账号在集群没有同名账号（无同名 OS 账号的纯平台管理员如 admin 属正常），改用代申请 |
| 端口提示“使用中” | 同一用户同一端口只能一个活跃实例；停机后即释放 |
| 作业提交失败“sbatch …” | 看 journalctl + 该作业日志；root 提交的 -o 勿落 /share（root_squash） |
| 提交报 `Invalid account or account/partition combination specified` | 该用户在 Slurm 会计里**没有账户关联**（集群开了 `AccountingStorageEnforce=associations`）。一条命令补：`portal-ctl ensure-assoc <用户>`。根因通常是该账号走的是「OS 账号已存在」开通路径 —— 那条路不经过 add-user.sh，历史上漏建关联；现已修：开通/初始化/提交前都会幂等补齐 |
| 作业日志报 `couldn't chdir to '/opt/cluster-portal'` | 作业继承了门户服务的 cwd（`WorkingDirectory=/opt/cluster-portal`，该目录只在管理节点有）。提交时显式加 `--chdir=<用户家目录>`；若仍出现，说明该节点上的 `portal-ctl` 不是最新版 |
| 用户 `ssh -p <端口> <用户>@<节点>` 报 **Permission denied (publickey)**，而密钥明明已登记 | 该节点上**存在重复 UID**。enroot 的 passwd hook（`/etc/enroot/hooks.d/10-shadow.sh`）只按 UID 执行一次 `getent passwd <uid>`，把取到的**那一条**记录写进容器 `/etc/passwd`；UID 重复时取到的是 `/etc/passwd` 里先出现的账号名，于是容器内**没有真实用户名条目**，sshd 解析不到该用户 → 拒绝（客户端只看到 publickey 失败）。**特征**：容器启动日志的"连接示例"里显示的是**别人的用户名**。排查 `awk -F: '$3>=1000{print $3}' /etc/passwd \| sort -n \| uniq -d`；修复：保留真正的用户、`userdel` 掉多余账号，然后重启该用户的作业（容器需重建）。`verify-install.sh` 已加该校验 |
| 同一用户在 `/share` 上的属组在各节点不一样 | 建号时只对齐了 UID、没对齐 GID（两个节点各自取号）。`portal-ctl` 现已同时下发 `-g <主节点GID>`；存量用户手工修正：`groupmod -g <主节点GID> <用户> && usermod -g <主节点GID> <用户>` |
| **设了额度却显示「不限」**；用户管理页出现橙色 `门户记 X ≠ OS` | 额度只写进了门户库、**没落到 OS**，而页面显示的是 `repquota` 实读值。根因：「OS 账号已存在」开通路径漏了 `set-quota`（管理员角色更是整段被 `if role=="user"` 跳过，`<USER>` 就是这样）。现已修：`existing` 路径（**含管理员**）都会初始化并 `set-quota`；页面新增「门户记录 ≠ OS」告警把这种不一致直接暴露出来。存量修复：用该行「改配额」重设一次，或 `portal-ctl set-quota <用户> <大小>` |
| 给 `root`/保留账号改配额报「不能设置具体配额」 | 属预期：系统保留账号不允许设**具体额度**（会威胁系统自身写入）。若要表示"不限额"，填/选「不限」即可 —— 门户库记为 `不限`、OS 为 soft=hard=0，两者一致、不再挂告警 |
| 「改配额」报 `配额只能在 admin 节点设置` | 该节点上的 `portal-ctl` 不是最新版：当前实现按「`/share` 是否为本地文件系统」判定（与 `add-user.sh` 同一口径），与主机名无关 |
| 镜像选了但起不来 | 该 .sqsh 未内置 sshd/start_ssh.sh（仅两个 cuda 镜像内置；测试用 tiny 镜像需自建该脚本） |
| 用户保存镜像失败/配额满 | 个人镜像写在 `<IMAGES_MOUNT>/<用户>/`。该目录**是否计入 /share 配额取决于站点**：若 `<IMAGES_MOUNT>` 与 `/share` 是同一个文件系统则计入；本站点把 `<IMAGES_MOUNT>` 做成了独立盘（`/dev/nvme0n1`），因此**不计入** /share 配额，需单独关注该盘容量 |
| 到期未见自动保存文件 | 到期自动保存在作业仍 RUNNING 时触发：若门户服务当时不可用、或用户磁盘配额写满导致导出失败，将跳过并在该资源行记录原因（提交时长含 15 分钟保存余量） |
| 忘记所有门户密码 | root 编辑 /etc/cluster-portal/users.passwd 全部重设 |
| 服务自动重启循环 | 看 journalctl；常见：数据目录属主/权限、sudoers 语法错误 |
| 管理员相互操作提示“由 root 管理” | 属预期：管理员生命周期归 root/OS root |

### 8.1 把 NAS / 数据集挂进用户容器（`EXTRA_MOUNTS`）

在 `/etc/cluster-portal/site.conf` 里配一项即可，格式 `<宿主路径>[:<容器内路径>][:ro|rw]`（默认 `ro`），多项用 `;`：

```conf
EXTRA_MOUNTS=/data:/data:ro;/mnt/nas219:/mnt/nas219:ro
```

改完不用重启：`portal-ctl` 每次调用都重新读站点配置。四条硬约束：

1. **只在服务端配置里配，不能做成页面上的选项**：门户 web 是不可信组件，若它能指定挂载，
   攻破门户就能把 `/var/lib/cluster-portal`（DB + Flask secret）挂进用户容器读走。
   `portal-ctl` 解析时会拒掉 `/var/lib/cluster-portal`、`/etc`、`/root`、`/proc`、`/sys`、
   `/dev`、`/boot`、`/run` 这些前缀。
2. **每台节点都要先挂上**（并写进 `/etc/fstab`，建议 `_netdev`），否则作业落到缺挂载的那台会在
   容器启动阶段 bind 失败 —— 用户只看到"提交成功、几秒后失败"。提交前 `portal-ctl` 会逐节点核对
   并直接拒绝，附可执行的提示。
3. **默认只读**：写共享盘会绕过 `/share` 的 usrquota，门户的额度显示与统计都不覆盖它。
4. NAS 侧挂载建议用 **`soft`**（或至少 `intr`）：`hard` 是无限重试，NAS 一抖，容器里的 I/O 卡在
   不可中断的 D 状态，`scancel` 都杀不掉，严重时只能重启节点。

随时自查：

```console
# 解析结果 + 每个节点缺不缺（只读，不产生副作用）
portal-ctl extra-mounts
#   {"mounts":[{"src":"/data","dst":"/data","flags":"ro"}],
#    "missing":{"admin":[],"gpu02":[],"gpu03":[]}}
# 完整验收里也会核对这一条（缺失即 FAIL）
verify-install.sh
```

> 共享盘上通常是历史遗留的 `777`，且 NAS 的 uid 与集群用户对不上（本站 NAS 是 1024/1025，
> 集群是 1001/1002）—— 挂进去等于**所有门户用户都能读改删**。要隔离得在 NAS 侧按集群 uid
> 建目录/收紧权限，那是另一件事，别指望挂载参数能解决。

## 9. 安全要点

- **（最重要）集群用户不得登录宿主机**：宿主机 sshd 必须做白名单
  （`/etc/ssh/sshd_config.d/10-portal-only.conf` → `AllowUsers root` + `PermitRootLogin prohibit-password`）。
  门户写进用户 `~/.ssh/authorized_keys` 的公钥是给**容器内** sshd 用的，而宿主机 sshd
  读的是同一个文件 —— 不做白名单，用户拿容器私钥就能登宿主机，并用 `sbatch/srun`
  绕过全部门户策略。做法与验收见 `base-cluster/all-in-one-cluster-manual.md` **1.7 节**；
  `oa/scripts/verify-install.sh` 已把该项纳入自检。
  **不要**用改 shell 为 `nologin` 的方式（会经 enroot passwd hook 传播，容器也登不进去）。
- web 以非特权 `portal` 运行；特权只经 `sudoers` 白名单 `/usr/local/sbin/portal-ctl`；
- 系统单元**不可**加 `NoNewPrivileges`（会断 sudo→portal-ctl）；单元已加
  `ProtectSystem=strict` + `ReadWritePaths=/var/lib/cluster-portal /etc/cluster-portal /share`；
  **`/share` 这一项不能漏**：`strict` 会把整个层级（含挂载点）挂成只读，而 portal-ctl 的活
  全在 `/share` 上（家目录、镜像、配额），且 `sudo` 子进程继承同一挂载命名空间；漏了它
  门户就"只能看不能动"（提交作业报 `Read-only file system: '/share/home/<用户>/.portal/logs'`）。
  `verify-install.sh` 已在服务的命名空间里试写 `/share` 来守这条；
  单元还要有 `BindReadOnlyPaths=/dev/sda`：`PrivateDevices=yes` 把块设备节点摘掉了，而
  `repquota /share` 必须先 `stat()` 它 —— 少了这条，「用户管理」页的配额列会**静默**整列变「—」，
  库里额度与 OS 实际值漂移（某用户库里 500G / OS 实际 5G）根本看不出来，直到他存镜像报
  `Disk quota exceeded` 才暴露。`verify-install.sh` 会在沙箱里调 `quota-all` 守这条；
- **应用代码归 root**（`/opt/cluster-portal/portalapp` 不允许 `portal` 可写）：
  `verify-install.sh`、`bootstrap.py` 会以 root 运行/导入这些模块，若 `portal` 可写，
  门户一旦被攻破，攻击者往代码里埋一行，等管理员跑一次自检就拿到 root。
  自检脚本本身也不再以 root 导入应用代码（改用标准库 sqlite3 读库）。
- `users.passwd` 明文含所有门户密码：保持 660/770、仅 root 与 portal 可读写，
  备份产物妥善保管（`backup-portal.sh` 已 `umask 077` + `chmod 600`）；
- **门户不托管 root 的宿主机密钥**：`_os_ok` 对 `root`/`portal`/`lab` 等系统保留账号一律返回假，
  保留账号也不能建门户账号、不能被提交作业、不能被注销 —— 否则「偷到门户 root 的口令」
  就等于「拿到宿主机 root」。
- **只有超级管理员 root 能创建管理员账号**（与「设为/取消管理员」同一条规则）；
- **会话有效期 12 小时（绝对过期）**：Flask 的 session 是无状态签名 Cookie，
  因此额外用 `users.session_epoch` 做吊销 —— 改密 / 管理员重置口令 / 停用账号 /
  权限变更 / 主动登出 都会 +1，旧 Cookie 立即失效。
  若在门户前面加了 TLS，记得设 `PORTAL_COOKIE_SECURE=1` 打开 Cookie 的 Secure 属性。
- authorized_keys 由门户统一管理（登记即整文件写回，删除即移除），不要手工混改；
  助手已拒绝在**符号链接**上读写（家目录在 NFS 上且容器 rw 挂载，用户可自建软链）。
- **容器不要以 root 运行**：`ENROOT_REMAP_ROOT` 保持 `n`，提交参数不加
  `--container-remap-root`（镜像内置 sshd 有固定口令 + PermitEmptyPasswords yes）。
  `verify-install.sh` 已逐台断言。

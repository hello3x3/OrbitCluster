01总览：一台作业的旅程

用户只看见一个网页；背后是“门户进程 + root 特权助手 + Slurm 调度器 + 节点上的 enroot 容器”四层协作。

四层各自负责什么

层角色关键点
网页门户用户唯一入口，普通权限进程会话 / 角色 / CSRF；只读写自己的 SQLite；需要特权时调用助手
root 助手门户与操作系统之间的唯一通道白名单子命令 + 参数校验（用户名、镜像名、路径、软链、端口范围）
Slurm排队与资源分配cgroup 限制 CPU/内存/GPU；时长含“保存镜像”余量
enroot / pyxis在每个节点上把镜像变成容器一作业一容器、共享宿主网络、可写 rootfs（保存镜像的前提）

02资源的完整生命周期

从“点申请”到“拿到 ssh”，再到“到期自动保存并停机”，一共九个阶段，都是可追踪的状态。

为什么“保存镜像”要放在停机之前？容器的可写层属于这次作业，作业一结束就被回收。所以提交给调度器的时长里 预留了保存所需的余量（默认 15 分钟），到期流程是“先导出镜像 → 确认完成 → 再停机”。

03门户与特权边界

网页进程本身没有任何特权；一切需要 root 的动作都必须经过一个只认固定命令的助手。

这么设计的好处：门户代码即使被塞进恶意参数（用户名、镜像名、端口），也最多得到一个“参数非法”的 JSON，而不是一个 root shell。
代价：每加一个需要特权的功能，都要在助手里新增一条子命令并单独校验，不能图省事直接 `sudo bash`。

04容器是怎么跑起来的

镜像是一个只读的 .sqsh 文件；作业启动时被展开成节点本地的一份可写 rootfs，容器就在那上面跑。

为什么不用 Docker

  • 集群节点不需要常驻守护进程，也不需要镜像仓库：一个文件就是一个镜像（.sqsh），放在 NFS 上人人可用；
  • 运行时不要求 root，普通用户在计算节点上就能把镜像跑起来；
  • 与 Slurm 的插件（pyxis）深度配合：sbatch --container-image=… 即可，不需要额外的编排层。

05三层存储与配额

同样在容器里，写在不同路径上的数据，速度、容量、生命周期完全不一样。这是最容易踩坑的地方。

一个容易忽略的细节：如果手工用 srun --container-image=… 起容器（没有给容器名）， 可写层会落在容器的内存文件系统（tmpfs）上——容量只有节点内存的一半左右，而且会占用作业自己的内存额度。 门户提交的作业走的是“命名容器 + 可写 rootfs”，落在节点本地盘上，容量大得多。

06镜像体系与原子导出

镜像分“公共”和“个人”；注释等元数据放在镜像同目录的同名 JSON 里，跟着镜像一起改名、一起删除。

操作谁可以做约束
改注释 / 改名 / 删除镜像归属者本人被“排队中”的资源使用时不能改名；被“排队/运行中”占用时不能删除
管理任意镜像（含公共）门户 root改公共镜像名会同步所有引用它的资源记录
名称规则—中英文数字与 . _ + -，不以点/横线/加号开头；新建个人镜像名 ≤ 32 字符，既有长名仍可管理
注释规则—最多 64 个“看得见的字符”（一个表情算一个），允许空格

07端口与网络

容器不建独立网卡，而是直接使用宿主机的网络；所以每个作业必须“提前认领”一个端口，容器内的 sshd 就监听它。

08账号、会话与权限

“门户账号”和“Linux 账号”是两套东西，门户把它们对应起来；权限完全由门户的角色决定。

09软件源与容器内环境

镜像里的包源统一指向教育网联合镜像站；而“环境变量”要同时铺到四条不同的入口，才不会出现“容器里查不到”。

10一份配置生成整套集群

所有站点差异都收在一个配置文件里；生成器把它展开成“每个文件怎么做”的清单，仓库本身保持通用。

11组件速查表

出事时先看这张表：每一件事都有一个“负责人”和一个“能看的地方”。

组件 / 文件作用出问题先看
cluster-portal.service门户进程（Flask + waitress）systemctl status / journalctl -u
/var/lib/cluster-portal/portal.db账号、资源、计划、事件日志页面上的“门户操作日志”
/usr/local/sbin/portal-ctlroot 特权助手（白名单子命令）直接手工执行同一子命令看 JSON
/etc/cluster-portal/site.conf站点差异（ssh 端口、镜像目录、套餐种子…）改完重启门户
slurmctld / slurmd排队与节点执行sinfo / squeue / sacct
/etc/enroot/enroot.conf容器数据/缓存目录、可写 rootfs 等节点上的 /scratch/enroot-data 占用
<IMAGES_MOUNT>/公共镜像（.sqsh + 注释 JSON）管理员可在门户里维护
<SHARE_MOUNT>/home/<用户>用户家目录（NFS）quota -s 看用量
/mnt/nas/*数据集 / 权重（大容量）节点上是否挂载成功
MANIFEST.md生成物下发清单部署时按它逐项落地
一句话总结：网页负责“说清楚想要什么”，助手负责“安全地去做”，Slurm 负责“什么时候在哪台机器上做”， enroot 负责“把它装进容器里跑”；而所有需要保留的东西，都不在容器里，而在 NFS 和镜像上。

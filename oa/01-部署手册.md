# 01 部署手册（在全新机器上复现本系统）

> 目标机器结构（本实例）：1 台管理/登录节点 + 2 台 GPU 计算节点，各 1×RTX 3060；
> 门户部署在管理节点（`<ADMIN>`），监听 `0.0.0.0:8000`。
> **先做两件事**：① 在仓库根目录执行 `make`，生成本集群的配置与**实值版文档**
> （见 `provision/README.md`）；本手册**自身**会被就地替换成实值版，
> 里面的 `<ADMIN>` / `<GPU01>` 已填成真实值，照那份做最省事。② 读 `config-snapshot/env-notes.md`
> 了解现场参数。
> 前置条件：底层集群（NFS / Slurm / enroot）已按 `base-cluster/` 部署并**验收通过** —— 门户依赖它。
>
> **若目标集群与上面这套不同**（节点数 / 卡型 / ssh 端口不一样），不要改代码：
> 照 `sites/3090-2node/` 做一个自己的 `sites/<站点>/`（`site.conf` + `plans.json`），
> 安装时作为第 3 个参数传给 install.sh 即可。站点无关的部分见下文第 2 节。
> 另一套已落地的实例：`sites/3090-2node/`（2 节点，各 3×RTX 3090，sshd 2022，镜像独立盘）。

## 0. 前置清单（缺一不可）

- [ ] 三台 Ubuntu 24.04 Server（Minimized），已配静态 IP/主机名/互访（见底层手册 1.2-1.3）
- [ ] **root 可经 ssh 登录**每台节点（本实例 sshd 端口 `2180`）；`<ADMIN>` 可免密 ssh root 到 `<GPU01>/<GPU02>`
- [ ] 底层集群已按 `base-cluster/all-in-one-cluster-manual.md` 部署并验收（**必须含**：会计 slurmdbd、
      配额、多用户建号脚本 `/opt/cluster-admin/add-user.sh`、enroot/pyxis）
- [ ] 管理节点可访问 PyPI（门户安装需 pip 装 flask/waitress；或用离线 wheels）
- [ ] 已准备至少一个**内置 sshd + /opt/start_ssh.sh 的 .sqsh 镜像**放入 `/share/images/`
      （实例为两个 cuda 镜像；其它镜像也能列出，但交互 SSH 需镜像内有 sshd）
      → 镜像的 **Dockerfile 构建源在 `base-cluster/images/<镜像名>/`**，重建步骤与加固要求见
      `base-cluster/images/README.md`（⚠️ 构建时必须用其中的**加固版** `start_ssh.sh`）
- [ ] 时钟已同步（munge 依赖）

## 1. 上传门户代码（在任一台能连 <ADMIN> 的机器执行）

```bash
scp -r oa/cluster-portal root@<ADMIN>:/tmp/cluster-portal-src
# 若目录带子目录，展开后得到 /tmp/cluster-portal-src/{deploy,portalapp,...}
```

## 2. 一键安装（在管理节点以 root 执行）

```bash
bash /tmp/cluster-portal-src/deploy/install.sh /tmp/cluster-portal-src 8000
# 有站点目录时（推荐，见 2.1）：
# bash /tmp/cluster-portal-src/deploy/install.sh /tmp/cluster-portal-src 8000 /tmp/site-<站点>
```

脚本将自动完成：
1. 创建运行账号 `portal`（nologin）与数据目录 `/var/lib/cluster-portal`；
2. 代码部署到 `/opt/cluster-portal`，`python3 -m venv` 安装依赖（flask、waitress）
   —— 缺 `python3-venv` 时自动 `apt install`；
3. 安装 root 助手 `/usr/local/sbin/portal-ctl`，写入 sudoers 白名单
   `/etc/sudoers.d/cluster-portal`（仅放行 portal→portal-ctl），并 `visudo -c` 校验；
4. 生成 `/etc/cluster-portal/users.passwd`（root:portal 660，目录 770，明文密码文件）；
5. 安装站点配置 `/etc/cluster-portal/site.conf`（给了第 3 个参数时）与套餐种子 `plans.json`；
6. 写 systemd 单元 `cluster-portal.service` 并 enable/start（waitress，0.0.0.0:8000，32 线程）；
7. 初始化默认管理员账号 `root`（平台最高管理员，集群同名 OS root 存在、可自助申请），
   随机密码写入 `/root/.cluster-portal-admin`（600，仅 root 可读）。

> 安装器可重复执行（幂等）：代码增量覆盖、不覆盖已有 `users.passwd` / `portal.db` / 管理员密码。

### 2.1 站点配置（换集群时唯一需要准备的东西）

门户代码**不写死** ssh 端口、节点名、GPU 型号：

| 项 | 来源 | 换机器要做什么 |
|---|---|---|
| 节点列表 / 分区名 | `sinfo` 运行时探测（`portal-ctl compute_nodes()/partition_name()`） | 不用改 |
| 节点 IP | `/etc/hosts` 解析（取最后一条非回环地址） | 不用改，写好 hosts 即可 |
| 节点间 ssh 端口 | `site.conf` 的 `SSH_PORT` | **要改**（默认 2180；3090 站点为 2022） |
| GPU 型号展示名 | `site.conf` 的 `GPU_MODEL_MAP`；纯数字 token 自动补 `RTX ` 前缀 | 一般不用改 |
| 套餐种子 | `site.conf` 的 `SEED_PLANS` 指向的 JSON | 按机型改 |
| 透传给容器的额外共享盘（NAS/数据集） | `site.conf` 的 `EXTRA_MOUNTS` | 要挂 NAS 时才配 |
| 宿主机上的 NAS 挂载 | 各节点 `/etc/fstab`（**不在 site.conf 里**） | 要用 NAS 就按 **2.2** 做 |

站点配置也能用环境变量覆盖（`PORTAL_SSH_PORT` 等），优先级：环境变量 > site.conf > 代码默认值 ——
但这条**对 root 助手不成立**，坑与全部字段说明见 **2.1.1**。
`/etc/cluster-portal/site.conf` 会被门户进程与 root 助手 `portal-ctl` **同时**读取。

#### 2.1.1 `site.conf` 完整字段、示例与生效方式

| | |
|---|---|
| 路径 | `/etc/cluster-portal/site.conf`（默认；可用 `PORTAL_SITE_CONF` 覆盖） |
| 权限 | `root:root 644` —— 本文件**不含任何密钥**，只描述这套集群的形状 |
| 格式 | 每行 `KEY=VALUE`；`#` 起注释；键名大小写不敏感 |
| ⚠️ 写法 | **值不要加引号、行尾不要写 `;`**（不做 shell 解析，引号/分号会被原样算进值里 —— 后果见下） |
| 读取方 | 门户进程 `portalapp/siteconf.py` **和** root 助手 `deploy/portal-ctl`（两套独立实现，同一个文件） |

> **引号 / 分号的后果**（都是实测过的）：`SSH_PORT="2180"` → 助手侧变成 `ssh -p '"2180"'`，
> 直接失败，建号/提交/保存镜像全挂；门户侧的「保留端口」列表还会**静默**漏掉这个端口
> （`db.py` 里 `int()` 失败被 `except` 吞掉，只当没配）。
> `EXTRA_MOUNTS` 的值里**可以**用 `;` 分隔多项（解析时按 `;`/换行切分、空项跳过），
> 但**别的键后面别加 `;`**，那会变成值的一部分。

**完整示例**（照抄改值即可；示例就是本站当前的内容）：

```conf
# 节点间 ssh 端口（门户助手 ssh/scp 到计算节点建号、提交、保存镜像都用它）。
# 该端口同时会被自动加入「用户不可申请的保留端口」列表。
SSH_PORT=2180

# gres 型号 token -> 界面展示名（纯数字 token 本来就会自动补 "RTX " 前缀，
# 这里显式写出只为可读性与将来改名方便）
GPU_MODEL_MAP=3060:RTX 3060

# 集群信息不可用（slurmctld 未起/查询失败）时的兜底 GPU 型号
DEFAULT_GPU_MODEL=RTX 3060

# Slurm 会计账户名（sacctmgr account），与 add-user.sh 的 CLUSTER_ACCOUNT 一致。
# 用户必须在这个账户下有关联，否则在 AccountingStorageEnforce=associations 的集群上会被拒。
ACCOUNT=lab

# 首次建库时的套餐种子 JSON（可选；缺省用内置 5 条）
SEED_PLANS=/etc/cluster-portal/plans.json

# 透传给用户容器的额外共享盘（NAS/数据集）。详见 2.3。
# 格式：<宿主路径>[:<容器内路径>][:ro|rw]，默认 ro；一行一项，可以写多行。
# ⚠️ 这里只是"允许挂进容器"的白名单，宿主机上还得真的挂上（见 2.2）——两件事都要做。
# EXTRA_MOUNTS=/mnt/nas/share:/mnt/nas/share:rw
# EXTRA_MOUNTS=/mnt/nas/datasets_tmp:/mnt/nas/datasets_tmp:rw
```

**每个键谁在读、改完要不要重启** —— 这是最容易踩的一点：

| 键 | 读取方 | 改了之后 |
|---|---|---|
| `SSH_PORT` | 门户进程（`siteconf.py`，**进程启动时读一次**）+ portal-ctl（每次调用重读） | **必须 `systemctl restart cluster-portal`** |
| `GPU_MODEL_MAP` / `DEFAULT_GPU_MODEL` | 门户进程（同上） | 同上，要重启 |
| `ACCOUNT` | 门户进程 + portal-ctl | 同上，要重启 |
| `SEED_PLANS` | 门户进程，且**只在首次建库**时用 | 重启；已建库的改这个键没用（改套餐走页面「资源套餐」） |
| `PARTITION` | 门户进程（预留；默认按 `sinfo` 探测） | 重启 |
| **`EXTRA_MOUNTS`** | **只有 portal-ctl**（每次调用才读文件） | **不用重启**，下一次提交作业就生效 |

> 一句话：**除了 `EXTRA_MOUNTS`，其它键改完都要重启 `cluster-portal`**。
> 因为 `siteconf.py` 是在进程启动时把配置读进内存的（模块级常量），而 `portal-ctl` 是每次被调用才读文件。

**关于「环境变量优先级最高」的一个坑**：文档里写的优先级（环境变量 `PORTAL_<KEY>` > site.conf > 内置默认）
只对**门户进程**成立（例如写进 systemd 单元的 `Environment=PORTAL_SSH_PORT=2022`）。
**对 root 助手不成立**：助手是门户经 `sudo -n` 调起来的，而 sudoers 里只有
`portal ALL=(root) NOPASSWD: /usr/local/sbin/portal-ctl`（没有 `env_keep`/`SETENV`），
sudo 默认 `env_reset` 会把变量丢掉。实测：

```bash
PORTAL_EXTRA_MOUNTS=/data:/data:ro runuser -u portal -- sudo -n /usr/local/sbin/portal-ctl extra-mounts
#   → raw 仍是 site.conf 里的值，/data 没生效   ← 环境变量没穿过去
```

所以**要改助手侧的行为（含 `EXTRA_MOUNTS`），请改文件，别只靠环境变量**。
（直接在 root shell 里跑 `/usr/local/sbin/portal-ctl` 调试时，环境变量是生效的 —— 差别就在 sudo。）

**怎么自查**：

```bash
# 助手侧（EXTRA_MOUNTS / SSH_PORT）：直接问助手，最准
/usr/local/sbin/portal-ctl extra-mounts
#   → {"source":"site.conf", "mounts":[...], "missing":{"<ADMIN>":[],...}}

# 门户进程侧：改完重启服务，然后看页面验证（都不需要 import 应用代码）
systemctl restart cluster-portal
#   SSH_PORT          →【个人资料】里试着登记 SSH_PORT 那个端口号 → 应被拒
#                       （提示"端口 N 属于常用/保留端口，不能申请"）
#   GPU_MODEL_MAP /   → root 进【资源套餐】→ 新增/编辑套餐时「GPU 型号」下拉的选项，
#   DEFAULT_GPU_MODEL   就是映射后的名字（节点信息拿不到时用兜底型号）
#   ACCOUNT           →【我的资源】的"我的配额/额度"卡片里显示"计费账号 <ACCOUNT>"
```

> ⚠️ 别为了"打印配置"用 root 去 `import portalapp.siteconf` —— 那正是安装自检
> （`verify-install.sh`）刻意避免的提权链：`portal` 若能写应用代码，root 一 import
> 就等于执行攻击者的代码。上面两条自查都不需要 import 应用代码。

### 2.2 挂载 NAS / 共享盘（要用 NAS 就**每台节点**都做）

门户自己**不挂任何东西**：它只是把「宿主机上已经存在的目录」按白名单 bind 进用户容器（见 2.3）。
所以 NAS 必须在 **<ADMIN> + 每一台计算节点**上都挂好，而且**必须写进 `/etc/fstab`**，
否则节点一重启就消失，作业会在容器启动阶段 bind 失败（用户只看到"提交成功、几秒后失败"）。

#### 2.2.1 先确认导出真的存在、网络真的通（别直接抄 fstab）

```bash
# 1) NAS 侧导出清单：要挂的路径必须在里面，并且允许本集群网段
showmount -e 10.71.106.245        # 例：会列出 /volume1/share、/volume2/datasets …

# 2) 每台节点都要能到 NAS 的 2049
for h in <ADMIN> <GPU01> <GPU02>; do
  ssh $h 'for ip in 10.71.106.245 10.71.106.233 10.71.106.219; do
            timeout 3 bash -c "echo > /dev/tcp/$ip/2049" && echo "$ip OK" || echo "$ip NO"
          done'
done
```

> 导出名（`/volume1/share`）与 fstab 第一段必须**逐字一致**；拼错一个字符就是挂在启动阶段报错。

#### 2.2.2 写 fstab（每台节点）

```fstab
# ---- OrbitCluster: NAS 共享盘（BEGIN orbitcluster-nas）----
10.71.106.245:/volume1/share        /mnt/nas/share          nfs     defaults,_netdev,nofail        0       0
10.71.106.245:/volume2/datasets     /mnt/nas/datasets       nfs     defaults,_netdev,nofail        0       0
10.71.106.245:/volume2/datasets_tmp /mnt/nas/datasets_tmp   nfs     defaults,_netdev,nofail        0       0
10.71.106.233:/volume1/share2       /mnt/nas/share2         nfs     defaults,_netdev,nofail        0       0
10.71.106.233:/volume2/datasets2    /mnt/nas/datasets2      nfs     defaults,_netdev,nofail        0       0
10.71.106.233:/volume3/datasets3    /mnt/nas/datasets3      nfs     defaults,_netdev,nofail        0       0
10.71.106.219:/volume1/datasets4    /mnt/nas/datasets4      nfs     defaults,_netdev,nofail        0       0
# ---- END orbitcluster-nas ----
```

**`_netdev,nofail` 不是可选项**：

| 选项 | 不加的后果 |
|---|---|
| `_netdev` | systemd 会把它当本地盘排进 `local-fs.target`；NAS 不在线时**开机会卡住、甚至掉进 emergency** |
| `nofail` | 单台 NAS 故障就拖死节点启动。**能起来比什么都重要** —— 缺挂载由门户侧兜底报出来（见 2.3） |

**`defaults` 自带的 `hard` 要自己权衡**：`hard` 是"无限重试"，NAS 一抖动，容器里碰它的 I/O
会卡在不可中断的 D 状态，`scancel` 都杀不掉，严重时只能重启节点。怕这个就显式写 `soft`
（或至少 `intr`）。经验取法：**要写数据的共享盘用 `hard`**（宁可卡也别半途 EIO 丢数据），
**纯读数据集用 `soft`** 更安全。

#### 2.2.3 应用并逐台核对

```bash
# 每台节点上执行：
mkdir -p /mnt/nas/share /mnt/nas/datasets /mnt/nas/datasets_tmp \
         /mnt/nas/share2 /mnt/nas/datasets2 /mnt/nas/datasets3 /mnt/nas/datasets4
findmnt --verify                     # 校验 fstab 语法：出现 [E] 就别重启，先改回
mount -a
systemctl daemon-reload              # 让 systemd 认到新生成的 .mount 单元
for p in /mnt/nas/*; do printf '%-26s %s\n' "$p" "$(findmnt -no SOURCE $p)"; done   # 每个都必须非空
```

**开机顺序也要核一下**（确认 `_netdev` 真的生效）：

```bash
systemctl list-dependencies remote-fs.target | grep -c mnt-nas-   # 应等于挂载点个数
systemctl list-dependencies local-fs.target  | grep -c mnt-nas-   # 必须为 0！
```

#### 2.2.4 「用户写 NAS 时在 NAS 上是谁」——别按用户名想

NFSv4 `sec=sys` 只在网络上传 **数字 uid/gid**，NAS 侧按自己的规则映射。多数群晖/威联通共享
默认「所有用户映射为 admin」（all_squash）—— **实测本站就是这样**：

```
以普通用户(uid 1001) 写  → NAS 上记的属主 1025:100
以另一个用户(uid 1002) 写 → 1025:100
以 root(0)           写  → 1025:100        ← 连 root 都被改写成同一个号
10.71.106.219 上的盘     → 1024:100
```

这意味着（排障时一定会用到）：

- **NAS 侧看不出是谁写的**：`ls -l` 全是同一个账号；按用户算的配额也全记在 NAS 管理员头上；
- 能不能动，只取决于**目录权限位**：现在多是历史遗留的 `777` → 人人可读写删；哪天收紧成非 777，
  因为文件属主是那个匿名号而不是用户本人，**用户连自己刚写的文件都可能动不了**；
- 想按人隔离，只能在 NAS 侧改成「不映射」（no squash）并让 NAS 的 uid 与集群 uid 对齐
  （本站集群用户是 `1000/1001/1002`）—— 那是 NAS 管理员的活，门户侧管不了。

#### 2.2.5 挂载侧只读的共享盘，别在 2.3 里配 `:rw`

导出在 NAS 侧被设成只读时，**客户端挂成 `rw` 也没用**：实测 `10.71.106.245:/volume2/datasets`
连 root 去写都报 `Read-only file system`。这类盘在 2.3 里配 `:ro`，否则用户会把"写不进去"
当成权限问题来报障。

#### 2.2.6 回滚

```bash
cp /etc/fstab /root/fstab.bak-$(date +%Y%m%d-%H%M%S)     # 改之前先备份
# 回滚：删掉 orbitcluster-nas 段 → systemctl daemon-reload → umount -l <挂载点>
```

### 2.3 把共享盘透传给用户容器（`EXTRA_MOUNTS`）

格式：每项 `<宿主路径>[:<容器内路径>][:ro|rw]`，**默认 `ro`**；多项用 `;` 分隔。

```conf
# 只读共享数据集（三节点都要先挂上）
EXTRA_MOUNTS=/data:/data:ro;/mnt/nas219:/mnt/nas219:ro
```

四条硬约束（都别绕过）：

1. **只在服务端配置里配，绝不接受请求参数。** 门户 web 在威胁模型里是不可信组件：
   一旦让它传路径，攻破门户就能传 `--container-mounts=/var/lib/cluster-portal:/x`，
   把门户 DB 与 Flask secret 挂进用户容器读走。所以 `portal-ctl` 只从 `site.conf` /
   `PORTAL_EXTRA_MOUNTS` 读，并在解析时拦掉 `/var/lib/cluster-portal`、`/etc`、
   `/root`、`/proc`、`/sys`、`/dev`、`/boot`、`/run` 这些前缀。
2. **每台节点都必须真的挂上**（按 **2.2** 做，写进 `/etc/fstab` 并带 `_netdev,nofail`）。少一台，作业落到
   那台时会在容器启动阶段 bind 失败，用户只看到"提交成功、几秒后失败"。
   `portal-ctl submit` 会**预先逐节点核对**并直接拒绝，`portal-ctl extra-mounts` 可随时查：
   ```
   portal-ctl extra-mounts     # → {"mounts":[...], "missing":{"gpu02":["/mnt/nas219"]}}
   verify-install.sh           # 也会核对这一条
   ```
3. **默认只读。** 写共享盘会绕过 `/share` 的 usrquota（门户的额度与统计都基于 `/share`），
   还可能把别人在用的盘写满。
4. **NAS 上的挂载选项建议用 `soft`（或至少 `intr`）**：`hard` 的语义是无限重试，NAS 一抖动，
   容器里的 I/O 会卡在不可中断的 D 状态，`scancel` 都杀不掉，严重时只能重启节点。

> 另外：共享盘上通常是历史遗留的 `777`（uid 与集群用户对不上），挂进去等于所有人都能读改删。
> 要真正隔离，得在 NAS 侧按集群 uid 建目录/收紧权限，那是另一件事。

> ⚠️ `SSH_PORT` 必须与集群 sshd 实际端口一致，否则门户的建号/提交/保存镜像/读日志全部失败；
> 该端口同时会被自动加入「用户不可申请的保留端口」列表。

## 3. 门户账号初始化/迁移

方式 A：沿用旧机账号密码 —— 直接复制明文密码文件（最快且口令不变）：
```bash
scp root@旧admin:/etc/cluster-portal/users.passwd /etc/cluster-portal/users.passwd
chown root:portal /etc/cluster-portal/users.passwd && chmod 660 /etc/cluster-portal/users.passwd
systemctl restart cluster-portal      # 重启后 watcher 会按文件内容生效
```

方式 B：全新初始化/重置 —— 安装器默认已创建 `root`（最高管理员）；如需重置 root 密码或
另建管理员（含无同名 OS 账号的“纯平台管理”账号），用 bootstrap.py（root 缺省即 admin 角色）：
```bash
# 重置/创建 root（默认角色即 admin）：
PORTAL_DATA=/var/lib/cluster-portal /opt/cluster-portal/venv/bin/python \
  /opt/cluster-portal/bootstrap.py root '<新密码>' --force
# 创建另一个管理员（如纯平台管理员 admin，无同名 OS 账号则仅门户管理）：
PORTAL_DATA=/var/lib/cluster-portal /opt/cluster-portal/venv/bin/python \
  /opt/cluster-portal/bootstrap.py admin '<初始密码>' admin
```
然后编辑 `/etc/cluster-portal/users.passwd` 登记/修改各账号密码，约 20s 自动生效；
也可执行立即生效命令：
```bash
cd /opt/cluster-portal && PORTAL_DATA=/var/lib/cluster-portal ./venv/bin/python -c \
 "import sys;sys.path.insert(0,'.');from portalapp.db import DB;from portalapp import pwfile;print(pwfile.sync_once(DB('/var/lib/cluster-portal/portal.db')))"
```

## 4. 检查/重建“配置快照”内容

- **镜像**：无需登记，申请页自动读 `/share/images/*.sqsh`（确认文件已就位）；
- **套餐**：首次启动自动种子化 5 个套餐（CPU×2、GPU×3，RTX 3060/最长48h）。
  想与旧机一致，按 `config-snapshot/plans.json` 在「资源套餐」里核对/手工录入
  （字段：名称/说明/gpus/gpu_model/cpus/mem_gb/maxtime_h/启用）；
- **用户**：与旧机一致时建议方式 A 迁移；否则在「用户管理」开通
  （普通用户=自动建号三节点同步+配额+sacctmgr；或 OS 账号已存在=仅开通门户并自动导入其公钥）。
  `config-snapshot/users.json` 为现场清单（无密码）；
- **root 可自助申请**：root 需先在“个人资料”登记 1 个端口；其 OS 公钥会被自动并入
  （登记首把公钥时门户会先把 `/root/.ssh/authorized_keys` 现有公钥导入，不会覆盖失联）。

## 5. 验收（端到端）

> **前置（不做则整个模型不成立）**：底层集群必须已完成
> `base-cluster/all-in-one-cluster-manual.md` **1.7 节**的 sshd 加固
> （`/etc/ssh/sshd_config.d/10-portal-only.conf` → `AllowUsers root`，三台都要）。
> 门户写进用户 `~/.ssh/authorized_keys` 的公钥是给**容器内** sshd 用的，
> 而宿主机 sshd 读同一个文件 —— 不做白名单，用户拿容器私钥就能登宿主机。

```bash
# 服务/自检
systemctl status cluster-portal --no-pager | head -5
curl -fsS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8000/login   # 期望 200
bash oa/scripts/verify-install.sh 8000                                    # 全 OK
#   ↑ 自检里已包含：sshd 白名单生效、应用代码不属于 portal、
#     portal 不能写应用代码、三台 ENROOT_REMAP_ROOT=n

# 浏览器侧（或 curl 会话）：
# 1) 默认管理员 root 登录（初始密码见 /root/.cluster-portal-admin）→ 用户管理开通一个测试普通用户（自动建号三节点）
# 2) 测试用户登录 → 个人资料：粘贴公钥(ssh-keygen -t ed25519 的 .pub)、登记端口(如 28771)
# 3) 申请资源：任务名3-10字符、选镜像(cuda 镜像)、套餐(GPU 或 CPU)、时长≤套餐maxtime、
#    端口选刚才登记且空闲的 → 提交
# 4) 我的资源 → 等待运行 → 用登记的私钥执行：
#    ssh -p <端口> <用户名>@<运行节点>      （容器内 nvidia-smi 应见卡）
# 5) 日志可查看；停机后端口释放可再申请；节点留空时运行后自动回填真实节点
# 6) 计算节点上 id <测试用户> 应与 <ADMIN> 一致；sacctmgr/配额已关联
# 7) 【安全】同一条测试用户记录，再试宿主机端口：
#    ssh -p 2180 <测试用户>@<节点>          → 必须 Permission denied
#    ssh -p 2180 root@<节点>                → 正常（密钥）
# 8) 【安全】以 portal 身份跑助手，必须被拒：
#    sudo -n /usr/local/sbin/portal-ctl set-keys root 'ssh-ed25519 AAAA... x'   → ok=false

# NAS（如果按 2.2/2.3 配了共享盘）：
/usr/local/sbin/portal-ctl extra-mounts
#   → {"mounts":[{"src":"/mnt/nas/share",...,"flags":"rw"}, ...],
#      "missing":{"<ADMIN>":[],"<GPU01>":[],"<GPU02>":[]}}     ← 每个节点都必须是空数组
#   进容器核对（提交一个资源后，在<ADMIN>上以 root）：
#     PID=$(pgrep -f /opt/start_ssh.sh | head -1)
#     grep -c ' /mnt/nas' /proc/$PID/mountinfo      # 应等于配的挂载项数
#     grep -E '^Uid:' /proc/$PID/status             # 应为提交者的 uid，不是 root
#   对照：容器里**不该**看到没配进 EXTRA_MOUNTS 的宿主目录（如 /data）。
```

## 6. 与底层集群手册的关系

- 底层（NFS/Slurm/enroot/监控/多用户）一切以 `base-cluster/all-in-one-cluster-manual.md` 为准；
- 门户不重复部署这些组件，只调用既有工具：建号调用 `/opt/cluster-admin/add-user.sh`
  （管理节点建家目录+配额+sacctmgr；计算节点 `-u UID` 同步），作业以 `runuser -u <用户> -- sbatch` 提交
  （等价 `sudo -u`），节点互连用 `ssh -p <SSH_PORT> root@<node>`；
- 若底层 ssh 端口与默认不同：**不要改代码**，改 `/etc/cluster-portal/site.conf` 的 `SSH_PORT`
  （或安装时用第 3 个参数传站点目录）并重启 `cluster-portal`；分区名与节点列表是运行时探测（不用改）。
- `/opt/cluster-admin/{add-user,set-quota,show-quota}.sh` 直接取仓库
  `base-cluster/scripts/cluster-admin/`：这三个脚本**不写死主机名**，靠 `/share` 是不是本地
  文件系统自动判定自己是管理节点还是计算节点，因此两套集群通用。

## 7. 常见安装问题

| 现象 | 处理 |
|---|---|
| venv 创建失败 ensurepip | `apt-get install -y python3-venv` 后重跑 install.sh |
| 服务起不来：secret/db 权限 | 数据目录属主须为 portal：`chown -R portal:portal /var/lib/cluster-portal` |
| 服务起不来：NoNewPrivileges | 单元里**不要**开 NoNewPrivileges（会阻断 sudo 助手） |
| portal 无法写密码文件 | `/etc/cluster-portal` 须 770 root:portal；文件 660 root:portal |
| root / 任一账号登录提示密码错误 | 门户密码以 `/etc/cluster-portal/users.passwd` 为准（文件机制已接管），修改该文件或重置 |
| 默认管理员(root)初始密码丢失 | 删除 `/root/.cluster-portal-admin` 后重跑 install.sh，或用 bootstrap.py root --force 重置 |
| 计算节点建号失败 | 确认 <ADMIN> 可 ssh root@节点(2180)；/opt/cluster-admin/add-user.sh 会被自动同步，仍失败则手动补齐 |
| 提交资源"成功"但几秒后失败 | 多半是 NAS 挂载缺失（作业落到没挂那台的节点，容器启动阶段 bind 失败）。`portal-ctl extra-mounts` 会直接点出是哪台缺哪个路径，见 **2.2** |
| 节点重启后 NAS 全没了 | fstab 里没写（只在命令行挂过）。按 **2.2.2** 写进 `/etc/fstab`，务必带 `_netdev,nofail` |
| NAS 断线后作业卡死、`scancel` 杀不掉 | 挂载选项是 `hard`（无限重试）→ 进程卡在 D 状态。按 **2.2.2** 改成 `soft` 或加 `intr` |
| 容器里看不到 NAS，但宿主机上有 | 只挂载还不够，要在 `site.conf` 的 `EXTRA_MOUNTS` 里按 **2.3** 配白名单；改完不用重启，下次提交生效 |
| `EXTRA_MOUNTS` 配了但没生效 | `portal-ctl extra-mounts` 看 `source`/`missing`；若报 `ok:false` 是配置项格式错（解析 fail-closed），按报错提示改 |
| NAS 上文件属主不是用户本人 | 正常现象：共享盘开了 all_squash（全映射到 NAS 管理员），见 **2.2.4**。要按人隔离只能在 NAS 侧改 |
